Internal API

PowerSystemsUpdater.ATTRIBUTE_DERIVATIONS — Constant

Supplemental attribute fields mapped onto differently named PSY6 fields, by attribute type.

source
PowerSystemsUpdater.CONDITIONALLY_REQUIRED_FIELDS — Constant

Fields the schema requires only in some states, which their declared type cannot show: a VSC converter's setpoint is optional, but required for the quantity its control mode selects, and _vsc_setpoints writes only that one (VSC_SETPOINT_FIELDS).

source
PowerSystemsUpdater.CONTROL_OBJECTIVE_BANDS — Constant

The bands each schema-0.2 control_objective requires on a TransformerCircuit (its conditional allOf blocks). UNDEFINED, "no control block", requires none.

source
PowerSystemsUpdater.DATA_DISCRIMINATORS — Constant

Discriminators whose value is data the record already carries (a reservoir's level_data_type), rather than a unit basis the updater chooses and writes.

source
PowerSystemsUpdater.DIRECT_TYPES — Constant

PSY5 type names that map onto an identically named PSY6 model. Everything else needs a bespoke translate method.

source
PowerSystemsUpdater.DYNAMIC_REFERENCE_FIELDS — Constant

PSY5 fields linking a static device to its dynamic model (DynamicGenerator, DynamicInverter, ...). The 0.2 schema has no dynamic models, so the updater skips them; the link is dropped and the static device kept, rather than the device being skipped with its model. Each dropped link is recorded on the report (record_dropped_dynamic_model!).

source
PowerSystemsUpdater.MARKET_BID_COST_DEFAULTED_FIELDS — Constant

PSY6 required fields with no PSY5 counterpart, mapped to the builder for the zero-cost value that stands in. Unlike MARKET_BID_COST_SCALAR_FIELDS this is not a promotion of PSY5 data — PSY5 either has no field here at all or writes an explicit null — so it only applies when the value is missing, never overwriting one PSY5 did supply.

source
PowerSystemsUpdater.MARKET_BID_COST_SCALAR_FIELDS — Constant

PSY5 permits MarketBidCost.shut_down to be a bare scalar; PSY6 types it as a concrete InputOutputCurve. The schema sanctions this promotion: the field's description documents the "legacy scalar promotion", and its default gives exactly the InputOutputCurve/LinearFunctionData shape built here (Core/common.json). Promotes the scalar s into a constant function (proportional_term = 0.0, i.e. the multiplier, so the curve's value is just s) rather than dropping it — PSY5's use of 0.0 here is a real "no extra cost" curve, not a missing value. Built as a raw PSY5-shaped nested dict so the promoted curve goes through the ordinary ONEOF_DISCRIMINATORS injection on the recursive pass right after, instead of a second, hand-rolled discriminator mechanism.

PSY5's no_load_cost is NOT included here: PSY6's counterpart field is minimum_energy_offer (a /MWh curve, not the same physical quantity), and the schema documents the conversion as minimum_energy_offer = no_load_cost / P_min — P_min lives on the owning generator, not on this cost object, so the division cannot be done from here. Promoting the bare scalar into a curve without that division would silently mislabel a /h value as /MWh. Left unmapped and recorded on the report instead of forced.

minimum_energy_offer is separately defaulted below (MARKET_BID_COST_DEFAULTED_FIELDS) whenever PSY5 supplies no value at all: the field is required on the PSY6 struct, and Core/common.json documents this exact zero-cost shape as its schema default — the same default a codegen consumer without vendor extensions would fall back to.

source
PowerSystemsUpdater.MULTIPLIER_QUANTITY_KINDS — Constant

The physical quantity a normalized series scales back to, keyed by the PSY5 accessor that named the base.

Values are quantity_types names from SiennaSchemas' Core/units.json, the vocabulary PSY6's quantity_kind column draws on. With unit_system set to COMPONENT_BASE the values are dimensionless, so this is the only remaining record of what they measure.

The reservoir accessors (get_storage_capacity, get_storage_target, get_inflow) are deliberately absent: their quantity depends on the owning reservoir's level_data_type (a level is an energy, a volume, or a head), which is not resolvable from an association row. _quantity_kind reports those rather than guessing one.

source
PowerSystemsUpdater.ONEOF_DISCRIMINATORS — Constant

PSY5 type name -> (PSY6 discriminator property, discriminator value). PSY5 has no such field; the value comes from __metadata__.type, not a formula on the name.

source
PowerSystemsUpdater.PER_UNIT_PRONE_UNITS — Constant

Physical units PSY5 commonly stored per unit. A field PSY6 declares in one of these, whose PSY5 storage is not known, is reported instead of copied.

source
PowerSystemsUpdater.POWER_UNITS — Constant

Power-family units, in which a per-unit value is a multiple of a base MVA.

source
PowerSystemsUpdater.PSSE_CONTROL_CODE — Constant

PSY5's TransformerControlObjective values are PSS/E's COD codes. A PSS/E ext row's bands are only used when its COD agrees with the objective, so they describe that control.

source
PowerSystemsUpdater.PSY5_DEFAULT_VOLTAGE_SETPOINT — Constant

PSY5's default TapTransformer.voltage_setpoint (1.0 pu). Files from PSY5 versions before the field existed omit it; current PSY5 fills this default when it loads one.

source
PowerSystemsUpdater.PSY5_DEVICE_BASE_FIELDS — Constant

PSY5 fields stored per unit on the component's own base_power (the system base for a component with none): every field PSY5's descriptors mark needs_conversion, as (type, field) => conversion_unit. The unit names the physical quantity PSY5's getters convert it to (mva for power, ohm for impedance, ...).

source
PowerSystemsUpdater.PSY5_DURATION_PATTERNS — Constant

PSY5's duration encoding, one pattern per Dates.Period its writer emitted.

Ordered, and the first match wins, because the patterns overlap: P0DT3600.000S is a Millisecond while P0DT3600S is a Second, and P1M is a month while P0DT1M is a minute. This is the same ordered table the writer's own reader used.

source
PowerSystemsUpdater.PSY5_FIELD_RENAMES — Constant

PSY5 fields whose PSY6 counterpart has another name, applied by direct_translate before the field copy: (PSY5 type, PSY5 field) => PSY6 field.

source
PowerSystemsUpdater.PSY5_FUEL_UNITS — Constant

PSY5 FuelCurve has no fuel_units: its y axis is MMBTU per hour by PSY5 convention. PSY6 requires the field, so a FuelCurve without it gets "MMBTU".

source
PowerSystemsUpdater.PSY5_INTERNAL_FIELDS — Constant

PSY5 keys that never become PSY6 properties on the entity itself. services is carried separately as ServiceAssociation rows (_add_service_associations! in convert.jl), not as a field on the component; ext is carried in the document's own ext table, keyed by component id (_carry_ext! in convert.jl), which is also where any PSY5 field with no PSY6 counterpart is kept (under UNMAPPED_EXT_KEY); internal and __metadata__ are serialization scaffolding.

source
PowerSystemsUpdater.PSY5_STORAGE — Constant

PSY5 fields stored some way other than device-base per unit, which PSY5's descriptors do not record, keyed by PSY5 type and by the field's name as it reaches build_kwargs (after any translator rename, e.g. FixedAdmittance's Y → y). "*" matches any type. Each entry cites where the PSY5 convention is stated.

source
PowerSystemsUpdater.PSY5_TS_METADATA_ROOT_PATH — Constant

The HDF5 dataset PSY5 embeds its metadata SQLite database in.

Named here rather than read from IS.HDF5_TS_METADATA_ROOT_PATH because that constant no longer exists: IS moved its storage to InfraStore and dropped HDF5 entirely. The path describes the legacy on-disk format this package reads, so it belongs to the reader.

source
PowerSystemsUpdater.PSY5_TS_ROOT_PATH — Constant

The HDF5 group PSY5 keys its time series arrays under, one subgroup per time series UUID, each holding a data dataset plus module/type/data_type attributes.

Named here rather than imported because IS dropped HDF5 storage when it moved to InfraStore. The constant describes the legacy format this package reads, so it belongs to the reader.

source
PowerSystemsUpdater.RESERVE_DIRECTIONS — Constant

PSY5 carries reserve direction as a type parameter (VariableReserve{ReserveUp}); PSY6 carries it as a field with a different vocabulary.

source
PowerSystemsUpdater.SERIES_KEY_TYPES — Constant

PSY5 key types, by the association time_series_types each can name.

source
PowerSystemsUpdater.SERIES_REF_FIELDS — Constant

PSY5 fields that may hold a time series key, by owner type, and the PSY6 field that names the series by association id in its place.

source
PowerSystemsUpdater.SWITCHED_ADMITTANCE_LIMITS_FIELD — Constant

The PSY6 band SwitchedAdmittance.admittance_limits (PSS/E VSWLO/VSWHI) lands in, by control mode: the schema's voltage modes use voltage_limits, its reactive modes reactive_power_range_limits. FIXED and UNDEFINED use neither, so their band is kept in ext.

source
PowerSystemsUpdater.TAP_MOVING_OBJECTIVES — Constant

Objectives that move the tap rather than the phase angle. Schema 0.2 lets their actuator band, tap_ratio_limits, be omitted ("defaults to 0.9 to 1.1, PSS/E's own RMI/RMA defaults"), but PowerSystems 6 rejects a circuit with one of these objectives and no tap_ratio_limits (branchdata_checks.jl), so it is always written: from the PSY5 fields or PSS/E ext like the required bands, else the schema's documented default.

source
PowerSystemsUpdater.THREE_WINDING_BASE_POWER_KEY — Constant

The PSY5 pair base each winding's values are stored on (PSY5's _get_winding_base_power): star-leg r/x, rating_$suffix and the flows of the primary winding are per unit on base_power_12, the secondary's on base_power_23, the tertiary's on base_power_13. Used as the circuit's own base_power, so the values copy across unscaled.

source
PowerSystemsUpdater.TIME_SERIES_POINTER_TYPES — Constant

PSY5 sometimes embeds a time series key in a value field. Where PSY6 has a field that names the series instead (SERIES_REF_FIELDS), the key is carried across as that series' association id. Anywhere else, dropping it would yield a document that validates while having lost data nothing downstream could recover, so this errors instead.

source
PowerSystemsUpdater.TRANSFORMER_CONSUMED_FIELDS — Constant

Fields consumed directly by the TwoWindingTransformer container rather than by _circuit_source's allow-list or build_kwargs.

source
PowerSystemsUpdater.TYPES_WITHOUT_EXT — Constant

PSY5 types whose PSY6 model has no ext. PowerSystems' importer ignores a doc.ext entry for them (_merge_doc_ext! in its import_document.jl), so an ext on one is recorded as dropped rather than written where nothing reads it.

source
PowerSystemsUpdater.UNIT_BASES — Constant

Every value a unit discriminator can take, in the order a basis is preferred.

source
PowerSystemsUpdater.UNMAPPED_EXT_KEY — Constant

The ext key under which a component keeps the PSY5 values that have no PSY6 field, as Dict(field => value). A field of a nested struct is keyed Type.field (e.g. ImportExportCost.ancillary_service_offers). Values are as PSY5 stored them, including its per-unit basis; each one is also listed in the ConversionReport.

source
PowerSystemsUpdater.VARIABLE_OPERATION_COST_TYPES — Constant

PSY5 spells the variable cost field variable on these four cost types; PSY6 spells it variable_operation_cost. Renamed before the generic recursive copy so it routes through the ordinary field-copy path instead of recording an unmapped field and leaving the required variable_operation_cost absent.

source
PowerSystemsUpdater.VSC_SETPOINT_FIELDS — Constant

PSY5's VSC dc_setpoint_* and ac_setpoint_* each hold whichever quantity the converter's control mode regulates; PSY6 has one field per quantity, selected by the same mode. An AC_VOLTAGE setpoint belongs to ACBus.voltage_setpoint in PSY6, so it raises an error.

source
PowerSystemsUpdater.WINDING_GROUP_ALPHA — Constant

PSY6 drops WindingGroupNumber and keeps only the angle, in TransformerCircuit.alpha (radians).

A literal table, deliberately not -n * pi / 6: the enum is sparse, and its sign is inverted relative to the obvious reading — GROUP_1 is -30 degrees, not +30.

source
PowerSystemsUpdater.ArcEndVoltagePU — Type

Per unit of the base voltage of one end of the component's arc (end_index 1 for from, 2 for to): a converter setpoint referred to its own AC terminal.

source
PowerSystemsUpdater.BusIndex — Type

Bus voltage bases and arc endpoints of a PSY5 case, for impedance and voltage bases.

source
PowerSystemsUpdater.ComponentUnits — Type

What converting one component's fields needs: its PSY5 record and the bases around it.

source
PowerSystemsUpdater.DeviceBasePU — Type

Per unit on the component's own base_power (the system base for a component with none).

source
PowerSystemsUpdater.Ledger — Type

Maps PSY5 component UUIDs onto the document-wide unique integer ids PSY6 requires, and records components that were skipped so references to them can be detected rather than emitted as dangling integers.

It also keeps, per component, the PSY5 values that have no PSY6 field (unmapped, keyed by UUID), collected against owner, the component being translated (translate_component). They are written to the component's ext (_carry_ext! in convert.jl) rather than dropped.

series_refs holds the time series references deferred during translation (defer_series_ref!): a field that names a time series by its association id, which exists only once the sidecar's catalog is written.

source
PowerSystemsUpdater.Natural — Type

Already in the physical unit PSY6 declares.

source
PowerSystemsUpdater.NaturalPower — Type

Natural power (MW, MVA, MVAr), which a per-unit PSY6 field takes on the component's base.

source
PowerSystemsUpdater.NonPhysicalBase — Type

Marks a value whose PSY5 base is non-physical (a base voltage of 0 or less), so it has no value in the unit PSY6 declares: a data problem in the source, reported as an invalid value.

source
PowerSystemsUpdater.PerHour — Type

Natural, but per hour where PSY6 is per second (m3/h against m3/s).

source
PowerSystemsUpdater.PiecewiseStepLayout — Type

A PiecewiseStepData per timestep.

PSY5 stored each as an (n, 2) matrix — hcat(x_coords, [NaN; y_coords]) — NaN-padded along its first axis to a common width and stacked. InfraStore stores the same value as one self-describing matrix row, so the padding has to be read off and the row rebuilt.

source
PowerSystemsUpdater.Psy5ElementLayout — Type

How PSY5 laid out one timestep's value, keyed by the data_type attribute it wrote beside the array.

Only the layouts the PSY5 corpus actually contains are mapped. An unmapped one errors: the two stores agree on plain scalars and on nothing else, so passing unknown bytes through would have InfraStore decode them as a different value with no complaint from either side.

source
PowerSystemsUpdater.Psy5Storage — Type

How PSY5 stored a field's value.

source
PowerSystemsUpdater.Psy5TimeSeriesKind — Type

Which of InfraStore's time series a PSY5 time_series_type becomes.

DeterministicSingleTimeSeries is a stored array in PSY5 and a derivation in InfraStore: it shares its SingleTimeSeries' array and is re-described by InfraStore.transform_single_time_series!. So it stages nothing and is handled in _derive_forecasts! after every array is in the store.

source
PowerSystemsUpdater.RelativeTo — Type

A multiple of another PSY5 value: a level stored as a fraction of storage_level_limits.max, or a voltage in per unit of rated_dc_voltage. path names that value in the PSY5 record.

source
PowerSystemsUpdater.ScalarLayout — Type

One scalar per timestep. The only layout the two formats already agree on.

source
PowerSystemsUpdater.SeriesRef — Type

A PSY5 time series key embedded in a field (FuelCurve.fuel_cost), owned by the component owner_uuid. It is written as placeholder, a negative integer no association id can take, and replaced by the id of the association the key names once the catalog is written (resolve_series_refs in convert.jl).

source
PowerSystemsUpdater.SystemBasePU — Type

Per unit on the system base, whatever the component's own base.

source
PowerSystemsUpdater.SystemBasePUOnVoltage — Type

Per unit on the system base power and the voltage (kV) named by path in the PSY5 record, rather than a bus's: an LCC line's impedances, on the base of the circuit they sit in.

source
PowerSystemsUpdater.UnknownStorage — Type

Not recorded anywhere: PSY5 never annotated the field and it is not in PSY5_STORAGE.

source
PowerSystemsUpdater.UnverifiedUnit — Type

Marks a value whose unit could not be established; see convert_units.

raw's services list (PSY5's Device.services, also carried by branches and by GroupReserve for nested membership) names, per entry, a service this entity contributes to. PSY6 has no such field on the entity itself: the membership becomes one ServiceAssociation row per (service, entity) pair, mirroring how _add_supplemental_attributes! turns PSY5's attribute manager into association rows.

A band from the PSY5 transformer's own fields, with the PSY5 key it came from, or nothing. Tried first: any PSY5 system has these, whatever it was built from. PowerSystemsUpdater._band_from_psse_ext — Method
_band_from_psse_ext(
    ext::AbstractDict,
    band::Symbol,
    winding::Int64,
    objective::AbstractString,
    base_power::Real
) -> Union{Nothing, Dict{String, Any}}

A band from the PSS/E columns a PSS/E-sourced PSY5 system keeps in ext, for winding winding (1 for a two-winding transformer, 1-3 for a three-winding one), or nothing when they are absent or describe a different control (COD disagreeing with the objective).

PSS/E's VMA/VMI are the target band: per unit voltage for the voltage objectives, MVAr or MW for the flow objectives, converted here to per unit on the circuit's own base. RMA/RMI are the actuator band: the tap ratio for the tap-moving objectives, a phase shifter's angle limits (degrees) for the others.

PowerSystemsUpdater._check_transformer3w_top_level! — Method
_check_transformer3w_top_level!(raw::AbstractDict)

_winding_circuit fills each circuit's rating from rating_$suffix, whose PSY5 default is 0.0. PowerSystemsUpdater._control_block — Method
_control_block(
    raw::AbstractDict,
    objective_key::AbstractString,
    winding::Int64,
    base_power::Real,
    ctx::PowerSystemsUpdater.TranslationContext
) -> Tuple{Any, Dict{Symbol, Any}, Vector{String}}

The control_objective and bands to write on one circuit, and the PSY5 keys used for them.

Schema 0.2 requires, for each objective other than UNDEFINED, the bands in CONTROL_OBJECTIVE_BANDS; tap-moving objectives also get tap_ratio_limits (see TAP_MOVING_OBJECTIVES). Each band is taken from the PSY5 transformer's own fields where it has one (_band_from_fields), else from PSS/E columns in its ext (_band_from_psse_ext), else from PSY5's default for a field an older file omits (_band_from_psy5_default). If a required band is in none of these, the circuit is written with UNDEFINED (no control block) so the document stays valid; the PSY5 objective is recorded against objective_key in the report and kept in the component's ext.

PowerSystemsUpdater._decode_kwargs — Method
_decode_kwargs(
    _::Type{T<:InfrastructureCoreOpenAPIModels.APIModel},
    kwargs::AbstractDict{Symbol}
) -> Dict{Symbol, Any}

Decode every value in kwargs against T's own declared field type.

The PSY5->PSY6 translation pipeline stages plain Julia values — JSON-shaped nested Dicts built by translate_value, bare enum spellings as String ("COMPONENT_BASE", "UP", ...), resolved reference ids as Int — that the OpenAPI 1.1 generator's strictly typed, immutable structs do not accept as-is: the old 0.2 generator's untyped fields tolerated them, but a field like power_units::UnitSystem or shut_down::InputOutputCurve now rejects a bare String/Dict with a MethodError. ICOM.decode is the generated packages' public entry point for this (the runtime's _decode, under the name every consumer is meant to call), so this routes every hand-built kwarg through the one path that already knows how to turn a raw value into T's declared type, whatever shape that type is.

PowerSystemsUpdater._derive_forecasts! — Method
_derive_forecasts!(
    store::InfraStore.Store,
    rows::AbstractVector{<:AbstractDict}
)

Re-derive the DeterministicSingleTimeSeries rows as InfraStore derivations.

InfraStore.transform_single_time_series! works on every SingleTimeSeries of one owner category at a resolution at once, so it can only reproduce a PSY5 sidecar whose derived rows cover all of them. Both preconditions are checked before anything is written — one (horizon, interval) per category and resolution, and one derived row per static row — and a sidecar that breaks either aborts rather than silently gaining or losing forecasts.

The owner category matters because PSY5 derives forecasts for components only, as IS does (owner_category = InfraStore.Component): a supplemental attribute's static series, such as an outage probability, has no derived forecast and must not gain one.

normalize_single_window and require_uniform_forecast_grid are set the way IS sets them, because IS is what reads the result.

source
PowerSystemsUpdater._derive_minimum_energy_offer — Method
_derive_minimum_energy_offer(
    raw::AbstractDict,
    ctx::PowerSystemsUpdater.TranslationContext
) -> Any

PSY5's MarketBidCost.no_load_cost ($/h) is PSY6's `minimum_energy_offer` ($/MWh at the unit's minimum power), by the conversion the schema documents: no_load_cost / P_min. Pmin is the owning device's `activepowerlimits.min`, in MW. With no positive Pmin the cost is left for the copy to report and keep in ext.

PSY6 has no MonitoredLine: it is a Line whose operational_flow_limit is set. PSY5's flow_limits holds one maximum per direction, (from_to, to_from); PSY6 holds a min/max pair per direction, written flat in the document (from_to_min, from_to_max, ...). Each PSY5 value becomes that direction's max, and each min is 0.0, reading the PSY5 limits as bounds on the flow in each direction separately (the PSY6 field documents "minimum and maximum flow in each direction"). PowerSystemsUpdater.translate — Method
translate(
    _::Val{:SwitchedAdmittance},
    raw::AbstractDict,
    ctx::PowerSystemsUpdater.TranslationContext
) -> Vector{InfrastructureCoreOpenAPIModels.APIModel}

PSY5's SwitchedAdmittance, mapped as PowerFlowFileParser's PSS/E reader maps the same record (PowerFlowFileParser.jl/src/openapi/shunt.jl):

  • Y (PSS/E BINIT, the solved total) → solved_admittance, its susceptance. Left unset when Y is zero, so PSY6 sums the engaged blocks as PSY5 does.
  • initial_status (PSS/E Si, a per-block in-service flag) → number_engaged (a per-block step count).
  • Y_increase → y_increase; admittance_limits (PSS/E VSWLO/VSWHI) → the band its control mode uses (SWITCHED_ADMITTANCE_LIMITS_FIELD), else ext.

Where this is known not to reproduce PSY5, the component is reported under approximate mappings (_warn_switched_admittance_approximations). A non-zero conductance (real(Y)) has no PSY6 field: Y is kept in ext whole. PSY6 names a remote regulated bus by id, so a zero regulated_bus_number (no remote bus) is dropped and a non-zero one raises an error.

PowerSystemsUpdater.translate_value — Method
translate_value(
    value::AbstractDict,
    ledger::PowerSystemsUpdater.Ledger,
    report::ConversionReport
) -> Union{Int64, Dict{String, Any}}

Non-reference dicts are forwarded recursively rather than verbatim, so a nested oneOf (a CostCurve containing a ValueCurve containing FunctionData) gets its discriminator at every level in one pass. __metadata__ is left in place: the schemas allow the extra key.

A key whose PSY5 value is nothing is dropped rather than forwarded as JSON null, matching build_kwargs's top-level behavior: PSY6 optional fields (input_at_zero, and similar) are typed without null, so a present-but-null key fails schema validation where an absent key decodes to ABSENT.

Every resolved nested composite is also checked against its PSY6 fieldnames (_record_unmapped_nested_fields!), the same guard build_kwargs applies at the top level — otherwise a PSY5 field with no PSY6 counterpart inside a nested object (for example FuelCurve.startup_fuel_offtake) would be forwarded into the output silently instead of being recorded as a finding.

The component's voltage base (kV), from its buses: an injector's bus, or a branch's arc.
